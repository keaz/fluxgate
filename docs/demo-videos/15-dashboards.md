## Gotchas while recording

- Traffic generator (recorder only, never shown on screen). Run it before recording so "Evaluations Today", the timeline and "Evaluations By Feature" have data. `k6-tests/load_test.js` is the model: it posts to `/ofrep/v1/evaluate/flags/{key}` on the edge (`:38`, `:187`) with a bearer SDK key (`:42`, `:178`). Copy it and change four things: `FEATURE_KEYS` (`:70`) to `express-checkout` and `holiday-banner`; the key sent as `CLIENT_ID` (`:42`) to the `checkout-service` SDK key (`<clientId>.<apiKey>`, video 08 Gotchas); `USER_IDS` (`:90`) to several dozen unique ids; and the request context (`:162`) to `targetingKey` plus `country` (`US`, `CA`, `UK`) and `user_tier` (`free`, `plus`) with no `environment_id`, because a mismatching one answers 401 (video 08 Gotchas). Lower the rate or duration (`LOAD_TIERS`, `:28`) so the table does not fill with millions of rows, then run `k6 run --env BASE_URL=http://localhost:8081 ...`. `perf-test/` is for large-scale benchmarks and seeds its own features; do not use it for this video.
- Evaluation numbers arrive late. The edge flushes evaluation events every 30 seconds by default (`feature-toggle/feature-edge-server/CONFIG.md:58`, `:320`), so wait about a minute after the run before opening "Evaluation Analytics", and keep the generator running for a minute while recording "Evaluations Today". Dry run once: dashboards poll and use subscriptions, and the update indicator shows the last refresh.
- Metric data (video 15 only). "Metrics & Experiments" needs a metric and events per variant, and nothing in the earlier videos creates them. The metric is created on camera at 1:22 ("New Metric", "Key" `checkout_conversion`, "Name" `Checkout Conversion`, "Type" "Conversion", "Create Metric"; `pages/Metrics.tsx:233-297`). It must exist before any event is posted: tracking an unknown key fails with `metric checkout_conversion not found` (`feature-toggle-backend/src/logic/metrics.rs:242`). Stop recording after "Create Metric". Off camera, post events with a client's credentials to `POST /api/v1/metrics/track` (public route; body `clientId`, `clientSecret`, `events[]` with `metricKey`, `featureKey`, `environmentId`, `userContext`, `variant`, `value`; `feature-toggle-backend/src/rest/metrics.rs:329-355`, `:1855-1880`). For a conversion metric, a `value` above 0 counts as a conversion and every event is one sample (`database/metrics.rs:384-398`). Send a few hundred events for `classic` and `express` on Development, with a visibly higher conversion rate for one variant. The page reads hourly aggregates: the aggregator runs once at backend start and then hourly (`lib.rs:283-291`, `scheduler/metrics_aggregator.rs:21-41`), so run `docker compose -f docker-compose.demo.yml restart backend` after posting, or wait up to an hour, then resume at 1:41. The voiceover says only that aggregation runs every hour. Check the "Variant Comparison" bars and the "Experiment" tab before recording the rest. Not run live: the smoke test of the v1.2.0 images did not cover metrics.
- The voiceover says the demo data is generated. Keep that line: the numbers come from the generator, not real users, and the script never promises a winner. "Winner" and "Recommendation" are whatever the backend returns; with no data the panel reads "No winner: metric data is missing for the selected window." (`FeatureExperimentPanel.tsx:284`).
- Dry run with the real stack (2026-10-05): the traffic generator (a `curl` loop against the edge for both flags, 150 s, about 430 rounds) filled the table with `express-checkout` and `holiday-banner`. The metric events (400, 200 per variant, conversion about 12% for `classic` and 22% for `express`, drawn at random) were accepted with `{"processed":400}` using the `checkout-service` credentials as `clientId` and `clientSecret`, and after `docker compose -f docker-compose.demo.yml restart backend` the page showed Total Samples 400, `classic` 12.0% and `express` 17.5%, with Winner `-`. On the "Experiment" tab the same data gives Winner "No winner", Confidence 87.9% and the recommendation "No winner yet: express is leading, but guardrails have not passed."; raise the `express` rate or the sample count if the take needs a clear winner, and never promise one. The "Canary Rollback Gate" form sits above the "Samples" row on that tab, so scroll past it. The "Evaluation Timeline" has one point for the old video 08 traffic and a second one for the new run, so the line curves across a long gap: run the generator shortly before recording, or the chart looks sparse. The "Actors" list also holds rows for ids and services (a bare user id, `jira-integration-<id>` and `AI risk assessment`) next to `admin`, `priya`, `sam` and `Jira (Kasun)`; point only at the named rows. Audit Analytics opens on a 30 day window. The palette also lists the flag `holiday-banner` under "Features" when you type `audit`. Sign-in lands on the overview, not `/features`.
- Never open `/dashboard/rollout` ("Feature Rollout"): it shows hard-coded status (`pages/Dashboard/FeatureRollout.tsx:103`). Its item still sits last in the "Observe" group of the sidebar (`layout/navConfig.ts:69`) and in the palette "Jump to" list.
