## Gotchas while recording

- Events URL and the tunnel (what the recorder must do). The UI builds the URL as `<REST base URL>/integrations/jira/<integration id>/events` (`feature-toggle-ui/src/utils/jiraIntegrations.ts:11-17`). The REST base URL is `window.ENV.REST_HTTP_URL`, which the UI container writes at start from `BACKEND_PROTOCOL`, `BACKEND_HOST` and `BACKEND_PORT` (`feature-toggle-ui/docker-entrypoint.sh:12-16`; default `http://localhost:8080/api/v1`, `src/api/config.ts:9-12`). It is not `public_base_url`, which only builds single sign-on callback URLs (`feature-toggle/feature-toggle-backend/config.toml` comment), and not `allowed_origin`. The brief tied the Events URL to `public_base_url`; the code does not.
  1. Start a tunnel to the backend before recording, for example `cloudflared tunnel --url http://localhost:8080`, which prints an `https://<random>.trycloudflare.com` address. Jira Cloud calls the URL from the internet, so it needs a public `https://` address; only the path `/api/v1/integrations/jira/<integration id>/events` has to be reachable (`feature-toggle/docs/jira-integration/setup-guide.md` section 4).
  2. On camera, copy the URL as the page shows it (`http://localhost:8080/api/v1/integrations/jira/<integration id>/events`) and replace `http://localhost:8080` with the tunnel's `https://` address in a text editor before pasting it into Jira. Keep the path unchanged. This is what a viewer can do with the unmodified demo files, so the voiceover and callout at 0:33 say it.
  3. ngrok: its free tier shows a browser warning page for requests without a special header, so also add the header `ngrok-skip-browser-warning` with the value `true` to the Jira web request (`feature-toggle/docs/jira-integration/screenshots/README.md`, automation step 09). Not used on camera: recreating the `ui` container with `BACKEND_PROTOCOL=https`, `BACKEND_HOST=<random>.trycloudflare.com`, `BACKEND_PORT=443` and `WS_PROTOCOL=wss` makes the page show the public URL, but it needs a compose override file the viewer does not have.
  4. Check before recording. `curl -s -o /dev/null -w "%{http_code}\n" -X POST <events URL>` must print `401`: FluxGate answers 401 to any call without credentials, so it proves the tunnel reaches the backend. It does not prove the integration id, because a wrong id or path answers 401 as well (`setup-guide.md` section 6; checked on a scratch backend). The real proof is a dry run: save the Jira flow, move a throwaway ticket, and look for `Success` in the flow's audit log and a new row in the Event log. A 401 there means the secret or the integration id is wrong. Write-back goes the other way, from the backend to Jira over HTTPS, and needs no tunnel.
  5. Demo stack note: `docs/demo-videos/assets/docker-compose.demo.yml` sets `BACKEND_HOST=localhost` on the `ui` service. The browser calls that address directly (`feature-toggle-ui/docker-entrypoint.sh:14-15`), so from the host it has to be `localhost`; the file used to say `backend`, which only resolves inside the compose network. Checked live on v1.2.0: `http://localhost:3000/config.js` sets `REST_HTTP_URL` to `http://localhost:8080/api/v1`, so the page shows `http://localhost:8080/...` as the Events URL host, which is why step 2 replaces it.
- Jira-side wording is not in the FluxGate source, so the script writes it in backticks and plain text. The steps and field names come from `feature-toggle/docs/jira-integration/setup-guide.md` (section 2.1) and the real-site screenshots in `feature-toggle/docs/jira-integration/screenshots/jira-automation/`. The newest Jira Cloud says space, flow and work item; the guide's older wording is project, rule and issue (`Create rule`, `Issue transitioned`). Say whichever the sandbox shows.
- Secret handling. The secret appears once after create or rotate (`pages/JiraSettingsPage.tsx:189-203`, `:30-34`) and lives only in page state. Do not reload or leave `/settings/jira` before it is saved in Jira; if it is lost, click "Rotate secret" (`:235`) and use the new value in the Jira header. Never click "Rotate secret" on camera after the Jira flow exists. The header can be `Authorization: Bearer <secret>` or `X-FluxGate-Jira-Secret: <secret>` (`rest/jira_events.rs:121-134`). Show the secret only as `<redacted>`, blurred.
- Create form versus settings form. The create form has only "Name" and "Jira base URL (optional)" (`pages/JiraSettingsPage.tsx:124-145`) and sets the environment field to `labels` (`:282-287`). Aliases, "Jira approves in" and the rest live in the "Settings" card (`JiraIntegrationSettingsForm.tsx:100-219` in `components/jira/`), so the script creates first and edits second. Brief wording: the brief put the environment field, aliases and "Jira approves in" on the create step; in code they come after.
- Alias `prod`. The brief lists aliases without an example. The script maps the Jira label `prod` to the environment `Production`, and video 13 labels `CHK-142` with `prod`. A label that equals the environment name (`Production`) works without an alias, compared ignoring case (`feature-toggle-backend/src/logic/jira_rules.rs:39-77`). The environment field reads labels because the issue's labels name the environments; an issue with no matching label does nothing (event log: "No rule matched.").
- "Jira approves in" is a trust decision. The page warns: "In these environments a Jira status change approves without a FluxGate approver. Only add environments whose Jira workflow you trust to gate releases." (`JiraIntegrationSettingsForm.tsx:30-31`, `:205-209`). `setup-guide.md` section 1.1 repeats it: anyone who can move the issue to the approving status can release there; restrict that Jira transition, and keep Production out of the list unless the Jira workflow is your approval process. In this story Production is listed on purpose, so the voiceover says it. Without the entry, an approve rule is refused with `environment not approved by Jira` (`logic/external_change.rs:27,130`).
- Save order. The rules editor reads the saved integration for its warning (`pages/JiraSettingsPage.tsx:420-426`), so click "Save settings" with Production under "Jira approves in" before you add the approve rule; otherwise the row shows `No environment in this rule trusts Jira, so this rule will be refused.` (`utils/jiraIntegrations.ts:63-64`). Without any approve rule a deploy rule warns `No enabled approve rule: deploy works only after a person approves the request in FluxGate.` (`:65-66`).
- Rule rows. The labels "Jira status 1", "Action 1" and "Environments 1" are built from the row number (`components/jira/JiraRulesEditor.tsx:145,155,169`), so they are listed under Label exceptions; rows 2 and 3 repeat the pattern. Action options read "Request", "Approve", "Deploy" and "Roll back" (`:33-38`); the environment filter placeholder reads "All environments" (`:174`). The brief's rule actions `request`, `approve`, `deploy` are the stored values. Rules run top to bottom, and the status matches ignoring case and spaces (`logic/jira_rules.rs:81-92`).
- What each action does in code (`logic/external_change.rs:115-155`). `request` on a stage that is NOT_DEPLOYED, DEPLOYMENT_REJECTED or ROLLBACKED asks for a deployment through the normal path, so the approval policy creates a pending request. `approve` in a Jira-approved environment closes that pending request as approved by Jira (`logic/approval.rs:2386-2507`). `deploy` works only from DEPLOYMENT_APPROVED; from any other state it is refused with `not approved` and changes nothing (`external_change.rs:29,139-141`). `rollback` requests, and in a Jira-approved environment also approves and completes, a rollback.
- Native webhook card. "Generate" creates a second secret and shows it once (`components/jira/JiraNativeWebhookSecret.tsx:25-36,88`). The script only points at it; clicking it would leave an unused secret on the integration. The text on the card says: Paste this secret into the Secret field of a Jira Cloud webhook. FluxGate checks the X-Hub-Signature header (`:99`). A webhook without a secret is rejected (`setup-guide.md` section 2).
- Write-back. "Save write-back" must come before "Test connection": the page says "Tests the saved settings." (`components/jira/JiraWritebackSettings.tsx:200`) and shows "Set the Jira base URL above first." when the integration has no base URL (`:116`). The success text `connected as <display name>` comes from the backend (`feature-toggle-backend/src/rest/jira_integration.rs:707-710`); a failure reads `Jira returned 401` or `could not reach Jira: ...` (`:716-721`). Saving a token needs `FLUXGATE_ENCRYPTION_KEY`, otherwise the backend answers `encryption_key_missing` (`setup-guide.md`, Security). The Jira user needs Browse projects, Add comments and Link issues. Changing the Jira base URL host later clears the token and turns write-back off (`JiraIntegrationSettingsForm.tsx:112-114`). The token field is a password input; blur it anyway.
- Jira workflow. The sandbox needs the statuses In Review and Approved; the real-site setup ticked `Allow transitions from any status` so a ticket can move straight to any status (`screenshots/README.md`, section 3). Restrict who can make the Approved transition in a real workflow (`setup-guide.md` section 2.3).
- Access. `/settings/jira` and the "Jira" item need an admin or Team Admin (`layout/navConfig.ts:116-122`, `pages/JiraSettingsPage.tsx:460-478`, backend `logic/policy.rs:439-445`); `priya` and `sam` see "Access Denied". Everything in this video is `admin`.
- Doc mismatch worth knowing. `setup-guide.md` section 2.1 says the body `Issue data (Jira format)` does not say who moved the issue, so an approval shows no person. The real-site run in `screenshots/README.md` section 4 shows the Jira user in the event log with that body. Video 13 does not depend on either; do not narrate who moved the ticket.
- Verification status. The request, approve and deploy chain, the event log and the write-back text were run against a scratch backend with a fake Jira on localhost (details in the task report); a real Jira Cloud site was not used. Jira Automation can lag by several seconds, so trim waits in editing.
