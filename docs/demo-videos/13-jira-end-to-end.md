## Gotchas while recording

- The label is the trigger. FluxGate acts only on flags linked to the ticket and only in the environments the ticket names through the integration's environment field, which video 12 left as `labels` (`feature-toggle-backend/src/logic/jira_rules.rs:151-200`). Add the label `prod` before the first move. An issue with no matching label does nothing: the event log says "No rule matched." (`components/jira/JiraEventLog.tsx:56`) and no comment is posted (checked on a scratch backend). A label that matches no environment is listed as an unknown environment in the event and in the comment (`logic/jira_capture.rs:62-67`, `JiraEventLog.tsx:29`). The label `Production` would also work without the alias. In Jira, type `prod` in the issue's "Labels" field and pick the option `prod (New label)` (or the existing `prod`); a suggested label such as `Perf-Test-Prod` is a different label and does not map.
- Linking needs an admin or Team Admin. The "Jira" card sits on the Overview tab of `/features/:id`, not on the edit page, and shows its button only when `canEdit` is true (`pages/FeatureDetail.tsx:563`, `components/features/JiraLinksCard.tsx:20,94-99`). The button's visible text is "Add"; "Add Jira issue" is its `aria-label`, which is the name the brief used. Typing the issue URL makes `CHK-142` a link in the card and on the approval card (`utils/approvalRequestContext.ts:31-40`).
- Linking itself writes to Jira. The `external_link_added` activity row queues a web link job (`logic/jira_capture.rs:148-153,244-256`), so the FluxGate web link can appear on `CHK-142` a few seconds after linking, before any status change, with Production shown as DEPLOYMENT_REJECTED. Its title is `FluxGate: <flag> · <environment> <STATUS> · ...` in pipeline order and is updated in place (`logic/jira_writeback.rs:127-139`; URL `<ui base URL>/features/<id>`, which is `allowed_origin` unless `[jira] ui_base_url` is set, `config.rs:274-285`).
- What each move does, in code. In Review runs `request`: the stage is DEPLOYMENT_REJECTED, which is allowed to request again (`validation.rs:62-65`, `logic/external_change.rs:115-155`), so the normal path creates a pending approval request under the policy `Release approvals`. The card reads `Stage DEPLOYMENT_REJECTED -> DEPLOYMENT_REQUESTED for feature express-checkout`, reference `CHK-142`, reason `Jira status 'In Review'` (`logic/jira_rules.rs:179`); "Requested by" shows the id of the integration's shadow user, not a name. Approved runs `approve`: Production is under "Jira approves in", so the pending request is closed as approved with source `jira` and the stage becomes DEPLOYMENT_APPROVED (`logic/approval.rs:2386-2507`). Done runs `deploy`: from DEPLOYMENT_APPROVED the stage becomes DEPLOYED (`external_change.rs:139`). All three were run in order on a scratch backend (details in the task report).
- The Approved card. The green badge reads `Approved by Jira (<display name>, CHK-142)` when the event carries the Jira user, and `Approved by Jira (CHK-142)` when it does not (`utils/approvalRequestContext.ts:12-25`). With the body `Issue data (Jira format)` the scratch run had no user, so the badge showed only the key; check what the sandbox sends and do not narrate a person. The card counts `0 approvals` because Jira's approval is not a vote; "Votes" shows the `Approved by Jira (...)` line and the time instead (`pages/ApprovalsPage.tsx:1228-1239`). "Details" shows `Jira status: Approved` under "Request context" (`ApprovalRequestContext.tsx:63-70` in `components/approvals/`). Checked on a real Jira Cloud site: the event did carry the user, so the badge read `Approved by Jira (<display name>, KAN-4)` and "Request context" read `Jira status: <the status name that ran the approve rule>`; the Event log rows show the same display name after the status. Still do not narrate a person.
- Brief change: "explain `sam` set this up". `/settings/jira` and the "Jira approves in" field need an admin or Team Admin (`layout/navConfig.ts:116-122`, `logic/policy.rs:439-445`), and `sam` has the Approver role only (video 03), so the voiceover says the setup listed Production and does not name `sam`. FluxGate does not map Jira users to FluxGate users (`feature-toggle/docs/jira-integration/setup-guide.md` section 7), which is why the voiceover tells viewers to limit the Approved transition in Jira.
- Why Production was requestable. The rejected request from video 10 stays in the "Rejected" filter; Jira's request is a new one. A rejected stage may be requested again (`validation.rs:62-65`). If you ever re-record from a state where Production is NOT_DEPLOYED, the same script works.
- Refusal path, not filmed. Moving the ticket to Done before Approved gives `refused` with the reason `not approved` and changes nothing (`external_change.rs:29,141`), and Jira receives the comment line `express-checkout · Production: deploy refused: not approved`. Both were checked on the scratch backend. If the stage is frozen, the rule is refused with `freeze window <name>` and Jira cannot override it (`external_change.rs:268-316`); the `Holiday freeze` from video 11 is Inactive, so nothing blocks.
- Timing. The Approvals list polls every 30 seconds (`pages/ApprovalsPage.tsx:74,359`), so reload to see a new card at once. FluxGate processes the event while Jira waits for the web request; Jira Automation itself can lag several seconds. Comments and the link are queued, then sent by two background jobs that run every 5 seconds, so allow up to about 10 seconds (`setup-guide.md` section 6, status table). Cut the waits in editing. Checked live: after the Jira status change, the Pending card, the approval and the stage change were in FluxGate within about 2 seconds, and Jira's audit log showed each run as `Success` in about 2 seconds.
- Comments on the ticket come from two sources (`logic/jira_capture.rs:42-75,155-198,202-260`). One comment per Jira event lists each rule's outcome: `FluxGate: Jira status 'In Review'` over `express-checkout · Production: request applied`, then the `approve applied` and `deploy applied` lines. Human actions in FluxGate (approve, reject, deploy, rollback, kill switch) get their own comment such as `Approved for Production by <name>`, but not when Jira made the change, so this flow adds exactly three comments plus the refreshed web link. The comment author is the Jira user of the API token from video 12. In Jira Cloud the comment text shows as paragraphs.
- Comment history and the capture cursor. The write-back capture starts at the time the backend first ran and re-reads the 60 seconds before the newest activity it has seen (`scheduler/jira_writeback_capture.rs:29-31,96-116`). In this series nothing recent exists for `express-checkout` when `CHK-142` is linked, so no history appears. If you restore a snapshot and link within a minute of earlier activity on the flag, the ticket also receives comments such as `Approved for Staging by sam` and `Rejected for Production by sam`, with `Ref: CHK-142` (seen on the scratch backend). Wait a minute, or link before that activity.
- Event log. Events are kept 30 days, newest first (`JiraEventLog.tsx:146`); each row shows the time, the issue key, the status, the Jira user when sent, then Feature, Environment, Action, Outcome and Details (`:62-66`). Details read `DEPLOYMENT_REJECTED → DEPLOYMENT_REQUESTED`, `DEPLOYMENT_REQUESTED → DEPLOYMENT_APPROVED` and `DEPLOYMENT_APPROVED → DEPLOYED` (`:72,90`). The "Outbound" tab has the columns Created, Issue, Kind, Status, Attempts, Next attempt and Last error (`components/jira/JiraOutboundLog.tsx:136-142`); `comment` and `remote_link` jobs read `sent`, and a failed one reads `dead` with a Retry button.
- Jira's audit log. Real site: each run reads `Success`; expanding a run and its `Send web request` step shows only `Successfully published web request`, not FluxGate's response body. The delay checkbox from video 12 makes a non-200 answer (for example a 401 from a wrong secret) fail the run, because the flow's "Continue running the flow even if the request response is not successful" box stays empty. A refused rule answers normally, so it shows only in FluxGate's Event log. The CLI is not used in this video (controller ruling); the same data is in the Event log and the "Outbound" tab.
- Write-back untested. The dry run could not use an API token, so write-back stayed off: the `CHK-142` comments, the web link and the "Outbound" tab rows (`comment`, `remote_link`, `sent`) were not seen on real Jira. With write-back off the "Outbound" tab reads "No outbound jobs yet." and the ticket gets no comments. Re-check scenes 2:28 and 2:56 (Outbound) once video 12's write-back is connected.
- Boundary. Write-back adds comments and a web link only; it never moves a ticket or edits its fields, and there is no kill switch from Jira (`setup-guide.md` section 7; JI-54 is open). The script claims neither. The closing line says FluxGate never moves tickets, which is what section 7 states.
- Account: everything here is `admin`; nothing switches account. Reload `/approvals` if the team selector looks stale.
- State left behind: `CHK-142` linked to `express-checkout` and in Done with the label `prod`; Production DEPLOYED with a Jira-approved request in the "Approved" filter; the Jira event log holds three events; `holiday-banner` is untouched (Development DEPLOYED, Staging and Production NOT DEPLOYED), which video 14 needs.
