## Gotchas while recording

- The AI UI is hidden unless the backend has `TYPESAFE_API_KEY` and the team toggle is on (`feature-toggle-ui/src/hooks/useAiFeatures.ts:51-64`). The demo compose passes the key from `.env` in the compose folder (`docs/demo-videos/assets/docker-compose.demo.yml`), so append it there and run `docker compose -f docker-compose.demo.yml up -d backend`: compose sees the changed environment and recreates the backend container only; Postgres data and the encryption key stay as they are. A plain `docker restart` does not pick up a new `.env` value. Without the key `/settings/ai` shows "AI judgments are not configured on this server (TYPESAFE_API_KEY not set)" and the switches are disabled (`pages/AiSettingsPage.tsx:48,205-209`), and the policy form has no "AI risk mode" field (`modals/ApprovalPolicyFormModal.tsx:412`). Check once before recording by opening `/settings/ai`: the switches are enabled only when the key is present. The key never appears on screen.
- `/settings/ai` and its "AI assistance" item are for a system admin only, not a Team Admin (`layout/navConfig.ts:121`, `pages/AiSettingsPage.tsx:162-174`), and it is team-scoped, so the team must be selected. The four labels are "Approval risk triage", "Reason quality check", "Flag kind classification" and "Natural-language search" (`:25-40`). The data notice (`:46`) lists what is sent: flag keys, descriptions, purposes, tags, change diffs and free-text reasons, plus tag and owner names for search.
- Outputs vary. Everything Jev returns (risk level, reasons, kind, search chips, hints) is model output, so the voiceover says for example and never promises a result. For orientation, the repo's tuning fixtures expect: a banner or cosmetic change in a development or staging environment rates low, a small beta in production medium, and a safety control turned off in production high (`feature-toggle-backend/tests/fixtures/ai/approval_risk.json`); a placeholder such as `as requested` is weak and a reason with a cause is fine (`.../justification.json`). Re-run the take if the model returns something else; do not edit the voiceover to fit.
- Deviation from the brief: the reason `fix` is replaced by `as requested`. The hint component checks only reasons of at least 5 characters (`components/ai/ReasonQualityHint.tsx:11,42-44`), so `fix` never triggers it, and the check is debounced by 800 ms (`:13`). A reason that names a ticket key, a URL, an issue reference like `#12` or an incident id is accepted by a rule without a model call, and rule results are not shown as hints (`feature-toggle-backend/src/judgment/justification.rs:96-101`, `rest/ai.rs:300-302`, `ReasonQualityHint.tsx:78-79`). So keep `CHK-142` out of the Reason field; it goes in "External Reference". The hint text comes from the backend: `This looks like placeholder text.` and `Add the cause: an incident, ticket, bug, or customer impact.` (`justification.rs:36-37`).
- Deviation from the brief: the order of beats. The brief requests the change first and edits the policy afterwards. The policy mode in force when a request is created decides whether it is assessed at all (mode Off skips it, `logic/approval.rs:498-514`), and enforcement runs when the assessment finishes (`judgment/approval_risk.rs:396-427`), so a mode changed later does not affect an assessed request. The script therefore turns on the toggles, classifies, and sets the mode first, and does only two account switches (`admin` to `priya` to `sam`) instead of four.
- Risk-mode decision: "Require one extra approver when high", as README row 14 says. The extra approver is `min(policy count + 1, eligible approvers)` (`approval_risk.rs:290-308`), and the eligible approvers are enabled team members with the Approver role who are not the requester (`database/approval.rs:37-75`). Here that is `sam` alone, so nothing is added: the request needs one approval and the activity row records `extra_approver_skipped` (`approval_risk.rs:423-425`); the panel shows no extra-approver hint. Self-approval stays blocked (`logic/approval.rs:764-766`) and `admin` is not an eligible approver, so `sam` approving is the only path, and it works. Checked on a scratch backend with canned Jev answers: a high rating with one approver left `requiredApprovalsEffective` at 1 and `sam` approved alone; with a second Approver the same rating raised it to 2 and the approvals page would show `+1 approver required: high AI risk` (`pages/ApprovalsPage.tsx:101-112`). The voiceover claims neither outcome for the recording; it explains the cap. Avoid the auto-approve path: leave "Auto-approve After (hours)" empty and never choose "Block auto-approve when high" on camera (`feature-toggle/docs/ai-judgments/HANDOFF.md` section 4: auto-approval can stall silently after transient database errors). README row 14 End state is therefore true as written; the Staging request ends approved, stage DEPLOYMENT APPROVED, not deployed.
- The panel and its states (`components/approvals/AiRiskPanel.tsx`). It sits right after "Request context" in the detail (`pages/ApprovalsPage.tsx:913`). It reads "Assessing risk…" while pending (`:103`; the approvals page polls every 5 seconds meanwhile, `pages/ApprovalsPage.tsx:75-90`), then the level badge and a reasons list only when a threshold is crossed (`:120-133`), "Signals" with the raw scores and the model name (`:134-163`), and a footer "AI assessment. Advisory unless the policy says otherwise." plus `Policy mode: <label>` once the policies load (`:167-173`). The list card shows a badge `AI: <level>` (`:46-63`). The reasons are fixed backend strings such as `Widens production exposure` and `Weakens a safety control` (`approval_risk.rs:41-45`); a low rating has none, so expect no list for a Staging banner. The panel does not render at all if the request has no assessment, which happens when the toggle was switched on after the request.
- The assessment input has the Jira key. `build_input` sends the diff, the flag's key, description, purpose, tags and kind, the environment, the impact figures, and the typed External Reference and Reason (`approval_risk.rs:127-185`, JI-52). That is why the script types `CHK-142` as the reference for `holiday-banner`; no Jira link to this flag exists, so it stays plain text on the card. An approval made by Jira skips the assessment instead (`logic/approval.rs:2469-2475`, `setup-guide.md` section 1.2); not shown here.
- Slow or failed assessments. Each call has a 3-second timeout by default (`feature-toggle/docs/ai-judgments/HANDOFF.md` section 2), so a slow answer can fail and the panel then reads "Risk assessment unavailable. Approval works as usual." (`AiRiskPanel.tsx:107-111`); a pending row older than 10 minutes also reads as failed (`rest/approval.rs:703-713`). If that happens, cancel the request and request again. Fail-open is real: with a canned 503 from Jev the request was created at once, the assessment read `failed`, the required approvals stayed 1 and `sam` approved normally (scratch backend). The fail-open sentences in the voiceover rest on three on-screen texts: the panel above, "AI search unavailable" in the palette (`components/CommandPalette.tsx:147-149`), and the note in the policy dialog (`ApprovalPolicyFormModal.tsx:431`, enforcement fails open). The reason hint shows nothing when the check fails (`ReasonQualityHint.tsx:60-62`). Taking Jev down on camera is not scripted.
- Flag kind. Prepare `holiday-banner` off camera, before any AI toggle is on: video 06 created it with no description, purpose or tags, and the repo's fixtures expect a bare key to stay unclassified (`feature-toggle-backend/tests/fixtures/ai/flag_kind.json`; an answer under 0.5 confidence is dropped, `judgment/flag_kind.rs:22,182`). Add the description `Banner for the holiday sale` and the purpose `Show during the sale, then delete the flag` in "Edit" and click "Update Feature". Do it before the toggles: with "Flag kind classification" on, saving a content change queues a classification by itself, and "Classify existing flags" would then queue 0. "Classify existing flags" queues unarchived flags with no kind and no person's choice, and skips content that already has a done or pending judgment (`database/feature.rs:652-660`, `flag_kind.rs:389-460`, `rest/ai.rs:494-530`); `express-checkout` has the kind Release from video 06, so only `holiday-banner` counts, and the toast reads `Queued 1 flag` (`AiSettingsPage.tsx:152`; listed under Label exceptions). The button shows only when the flag-kind toggle is saved on (`:145`). Classification runs in the background; wait a few seconds before scene 2:52.
- Deviation from the brief: `/features` shows the kind but not that it came from AI. The list row only adds a kind badge (`components/features/FeatureTable.tsx:133-137`); the label "AI suggested" is on the edit page under "Kind" (`components/features/FlagKindField.tsx:52`, and only while the field is unchanged), and the detail page shows `Kind: <kind> (AI, <n>%)` (`pages/FeatureDetail.tsx:495-505`). The script uses the edit page and does not save it. If no kind appears after a minute, the model was not sure; add a purpose to the flag and classify again (a flag edit re-queues it).
- Deviation from the brief: the search question. `which checkout flags are on in production for Canada?` asks about live state, which this search cannot answer. It turns the sentence into the list filters (lifecycle, stale, expired, type, dependencies, approval status, kind, tag, owner) and, when a topic is left over, ranks by relevance (`judgment/nl_search.rs:1-60`, `lib/nlSearch.ts:41-54`); it never evaluates a flag per environment or context. The script types `release flags tagged checkout`, which maps to the kind and tag filters, so the chips read like `kind: release` and `tag: checkout` and `express-checkout` is the likely hit. The "Ask FluxGate" item needs the toggle and at least 3 words (`lib/nlSearch.ts:3`, `CommandPalette.tsx:81-86`); the chips and relevance percentages vary. "Open in list" opens `/features` with the same filters.
- Roles and accounts. `priya` needs the Requester role to see "Stage Change Details" and "Request Deployment" (`pages/FeatureCreate.tsx:2064`, video 10 gotchas); `sam` needs the Approver role for "Approve with comment" (`ApprovalsPage.tsx:1289`). "Update Feature" and the policy edit need `admin`. After switching users, reload the page if the team selector looks stale. The AI toggles are cached for a minute (`useAiFeatures.ts:20`); the command palette refetches each time it opens (`CommandPalette.tsx:70-74`).
- Verification status. The settings, the backfill count, the policy mode, the risk cap and the fail-open path were run on a scratch backend with a local stand-in for Jev that returns canned answers (details in the task report). The real TypeSafe API was not called, so the levels, hints, kinds and search chips named in this script are expectations from the repo's tuning fixtures, not observed results. Do a dry run with the real key before recording.
- State left behind: all four toggles on; `Release approvals` mode `require_extra_approver`; `holiday-banner` has an AI kind and a description and purpose; its Staging stage is DEPLOYMENT APPROVED (not deployed), Development DEPLOYED, Production NOT DEPLOYED; one approved request with a stored assessment; `express-checkout` unchanged.
