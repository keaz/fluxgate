## Gotchas while recording

- Policy already exists: `Release approvals` was created by `admin` in video 04 (All Environments, Approver role). This video never clicks "Create Policy". The tour only opens the existing policy from the pencil icon in the table (button `title="Edit policy"`, `components/tables/ApprovalPolicyTable.tsx:181`), which opens "Edit Approval Policy" (`modals/ApprovalPolicyFormModal.tsx:252`). Close it with "Cancel" (`:461` shows "Save Changes" in edit mode; do not click it).
- Field labels in the dialog, in order (`ApprovalPolicyFormModal.tsx`): "Policy Name" (`:264`), "Description", "Scope" with options "All Environments", "Production Environments Only", "Specific Environments" (`:296-298`), "Required Approvals" (`:326`; the brief called it "Required Approvers"), "Approver Roles" (`:342`), "Explicit Approvers" (`:354`), "Fallback to roles" and "Admin override" switches (`:371,384`), "Auto-approve After (hours)" (`:398`), "AI risk mode" (`:416`), "Enabled". "AI risk mode" renders only when AI is available (`aiAvailable`, which needs `TYPESAFE_API_KEY`); without the key the voiceover sentence about it should be cut.
- Role gates: the "Approval Policies" item under "Govern" needs an admin or `Team Admin` (`layout/navConfig.ts:99-106`, gate `teamsManagement`; `utils/auth.ts:116-122`), so `admin` opens it. The stage "Request Deployment" action needs the Requester role (`pages/FeatureCreate.tsx:776-782`, `utils/auth.ts:97-99`), and "Deploy" needs Requester or Approver (`FeatureCreate.tsx:759-766`). "Approve", "Reject", "Approve with comment" and "Reject with comment" are enabled only for the Approver role (`pages/ApprovalsPage.tsx:1280-1300`). Nobody approves their own request (backend `logic/approval.rs:660,762`), so `sam` does the votes.
- Deviation from the brief: the brief makes `admin` click "Create Policy". The controller ruling and video 04 already created the policy, so the first scenes are a field tour only.
- The "Stage Change Details" box (`FeatureCreate.tsx:2066`) holds "External Reference" (`:2073`, placeholder `PROJ-123 or a change id`) and "Reason" (`:2087`, placeholder `Why this stage change is needed`). It appears once a stage is selected, for users with the Requester or Approver role. Suggested reasons: Staging `Verify the express checkout rules before Production`, Production `Release express checkout to customers`. Type `CHK-142` in "External Reference" for the Staging request only; leave it empty for Production. The values are sent with the next stage action, and the toast reads "Stage change requested" (`:1028`). Both reach the approver under "Request context" (`ApprovalRequestContext.tsx:40`). The reference is plain text unless a Jira link exists (video 12).
- Policy preview banner: `ApprovalPolicyPreviewBanner.tsx`. Its title is "Approval required" for a policy that applies; it also shows "Policy", "Scope" and "Approvers" (`:112-123`) and the policy's role ids as `Role xxxxxxxx` chips. The banner shows once a stage is selected, before any button is clicked.
- After the request the "Actions" menu for `priya` reads "Approval pending – resolve it through the Approvals page" until `sam` votes (`FeatureCreate.tsx:2023`). After the approval the stage shows DEPLOYMENT APPROVED and "Actions" offers "Deploy". After the Production rejection the stage shows DEPLOYMENT REJECTED, and "Request Deployment" is offered again (`FeatureCreate.tsx:776-782`), so video 13 can request it again.
- Header pill: `layout/Header.tsx:90-108`; it is a link labelled "Approvals" with a count badge (`aria-label="pending-approvals-count"`) that appears only when the count is above zero. It is visible to every signed-in user with a team selected, not only to approvers. Click it to reach `/approvals`.
- Approvals page (`pages/ApprovalsPage.tsx`): heading "Approvals" (`:646`), filters "All statuses", "Pending", "Approved", "Rejected", "Cancelled", "Auto Approved" and "Mine" (`:65-72,125-131`). The page opens on "Pending". Each card has "Open Feature", "Details" (`:850`), "Approve", "Reject" and "Cancel". Detail sections, in order: "Request context" (`ApprovalRequestContext.tsx:37`), "Blast radius" (`:924`), "Dependency impact" (`:975`), "Structured diff" (`:1004`), "Approval policy" (`:1110`), "Approval routing" (`:1175`), "Status timeline" (`:1209`), "Votes" (`:1227`), then "Add a comment" (`:1271`) with "Approve with comment" (`:1289`), "Reject with comment" (`:1297`), "Cancel request" and "Clear selection".
- Deviation from the brief: "Dependency impact" renders only when the severity is above low (`ApprovalsPage.tsx:970`). `express-checkout` has no dependents, so the card does not appear in the recording. The voiceover at 2:04 therefore mentions it only as a condition (if the flag has dependents, the card appears) and does not point at it; strictly it needs dependents with an impact above low. Likewise "Blast radius" shows only when the request payload carries it (`:251-268`); stage changes do (`logic/approval.rs:1909`).
- Toasts: "Approval recorded" and "Request rejected" (`ApprovalsPage.tsx:568-570`). Without a comment the quick buttons send `Approved via approvals dashboard` or `Rejected via approvals dashboard` (`:584,590`); this video uses the detail buttons instead. A rejection comment is optional in code, so the voiceover says to give one rather than that it is required. Suggested approve comment: `Diff matches CHK-142, go ahead.`
- After switching users, reload the page if the team selector looks stale.
- After a vote the comment is not on screen until you look for it. `handleAction` refetches only the Pending list (`ApprovalsPage.tsx:553-565`; the Pending query asks for the `pending` status only, `hooks/usePendingApprovalRequests.ts`), so the voted request drops out of it (with the policy default of one required approval, `ApprovalPolicyFormModal.tsx:45`). The effect at `:449-459` then deletes the `requestId` search parameter because the request is no longer in the list, so the detail panel closes. Expect an empty Pending list and the toast, nothing else, after "Approve with comment" and after "Reject with comment". The comment can be read only in "Details" under "Votes" on the "Approved" or "Rejected" filter (the list response carries the votes, `feature-toggle-backend/src/rest/approval.rs:1090-1098`), which is why the last scene opens the "Rejected" filter. The "Rejected" list card itself shows the reason from `priya` (`ApprovalRequestContext.tsx`), not the comment, and no reference badge, because the Production request leaves "External Reference" empty: only the Staging request carries `CHK-142`. In video 13 Jira requests Production again with `CHK-142` as its reference.
- "Votes" prints the approver id, not the username: each line is `Approved by <approverId> — <comment> · Snapshot <8 characters>` or the `Rejected by` form (`ApprovalsPage.tsx:1243-1245`). `approverId` is the user's UUID (`approver_id: vote.approver_id.to_string()`, `rest/approval.rs:472`, from a `Uuid` column), so `sam` does not appear on that line; the card header also prints `Requested by <id>` (`:903`). The voiceover says so. Blur or crop the UUID if you prefer. The exact reject comment `Ship Production through CHK-142 so QA sign-off is tracked.` appears on screen only there. The "Rejected" filter needs the Production request to be the only rejected one; no earlier rejection exists in the story.
- Dry run findings (live, v1.2.0): the "Deploy" click as `priya` also raises the toast "Stage change requested" (the same toast as the request) and the stage banner switches to "Request Rollback", so the stage is deployed. The diff section of the Staging request carries the red tag "Production impact" even though the environment is Staging (a product quirk; the voiceover does not read it). "Approval routing" lists the eligible approvers by short id (8 characters), not by name. The sign-in button can need a second click right after typing the password; wait for the typing to finish.
- The "AI risk mode" field and the "AI Risk" column show in the dry run because the backend container inherited `TYPESAFE_API_KEY` from the shell. A viewer who has not set the key (it comes in video 14) sees neither, so keep the voiceover sentence about the field only when the key is set, and otherwise cut it.
