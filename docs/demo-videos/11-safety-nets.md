## Gotchas while recording

- Choice for the kill-switch target (controller ruling, option a): `holiday-banner` has no deployed stage through video 09 (stages are created `enabled: false` and become enabled only on deployment), so the kill switch would have nothing live to override and the video 09 gate script would already exit 10. The script therefore time-lapses the Development deployment (request by `priya`, approval by `sam`, deploy by `priya`) first. Video 09's Gotchas already say to record 09 before 11. Option (b), using `express-checkout`, was rejected because a version rollback restores the whole snapshot including criteria and stage statuses (`feature-toggle-backend/src/database/feature.rs:4138-4170,4332`), which could undo the hero flag's state that videos 12 to 13 depend on.
- State left behind: `holiday-banner` Development is DEPLOYED, Staging and Production are NOT DEPLOYED. A version rollback restores stage statuses from the snapshot, and the snapshot you roll back to was taken after the Development deployment (the emergency-enable version), so Development stays deployed. Video 14 requests a Staging deployment for `holiday-banner`; that is compatible.
- Role gates: "Freeze Windows" under "Govern" needs an admin or `Team Admin` (`layout/navConfig.ts:107`, gate `teamsManagement`). Creating, disabling and deleting windows needs the same (`feature-toggle-backend/src/rest/operational_safety.rs:1079,1162,1242`; the page controls are disabled otherwise, `pages/FreezeWindowsPage.tsx:81`). The "Override Reason" field shows only to an admin or `Team Admin`; everyone else sees "Team Admin or system admin access is required to override this freeze." (`pages/FeatureCreate.tsx:499,2135-2161`). Emergency disable and enable need an admin or `Team Admin` (`rest/feature.rs:70-79`), and scheduled disable, enable or archive needs the same as a feature update (`operational_safety.rs:284-306`). "Update Feature" is a `PATCH`, so it also needs an admin or `Team Admin`. A version rollback has no role check beyond sign-in (`rest/feature.rs:1406`). So `admin` does everything after the time-lapse.
- Deviation from the brief: the "Active change freeze" banner exists only on the Feature Rollout dashboard (`pages/Dashboard/FeatureRollout.tsx:375`), which this series never shows. On the stage editor the freeze appears as the "Change Freeze" card (`FeatureCreate.tsx:2113-2160`) with the badge "Frozen" (or "Open") and the text `<window name> is active for <environment>`, plus the "Override Reason" field (`:2138`). The script uses that card. The card only appears after you select a stage.
- Freeze window form (`FreezeWindowsPage.tsx`): section title "New Window" (`:170`), labels "Name", "Scope", "Recurrence", "Starts", "Ends", "Reason", button "Create Window" (`:270`); toast "Freeze window created". "Starts" defaults to 15 minutes from now (`:58`) and "Ends" to 75 minutes (`:59`), so a new window is not active yet and shows `Starts in 15 minutes` until you move "Starts" a few minutes into the past (the field is a `datetime-local` input). "Scope" lists each environment by name, then `All Development`, `All Staging`, `All Production` (built as `All {type}` at `:201`, so they are not quoted). Pick the environment `Production`. The table columns are "Window", "Scope", "Timing", "Status" and "Actions"; the row buttons are "Disable" and "Delete". "Disable" makes the status "Inactive" and keeps the window, which is how the script ends it. The window stays in the table afterwards.
- Why Production for the freeze: the freeze would otherwise block the Development deployment time-lapse and later edits. A window scoped to Production leaves Development alone, and the "Change Freeze" card still shows on the Production stage.
- Emergency buttons (`components/features/FeatureTable.tsx:783-800`): the list shows an icon button with the tooltip "Emergency Disable" (red) while the flag is on, and "Emergency Enable" (green) once it is off. There is no text on the button. The same action exists on the flag's detail page as a button with the text "Emergency Disable" or "Emergency Enable" (`pages/FeatureDetail.tsx:403`). The dialog title is "Disable Feature" or "Enable Feature" (`modals/FeatureEmergencyActionModal.tsx:215`); fields "Reason" (at least 5 characters, `:171`), "Disable timing" with options "Disable immediately" and "Schedule disable" (`:281-282`), an optional "Expiry", and a confirm button "Disable Feature" (or "Schedule Disable"). The brief called the title "Disable immediately"; in code that is the option. The row then shows "DISABLED" and the red box "EMERGENCY OVERRIDE" with the reason (`FeatureTable.tsx:96`). The toast reads `Feature "holiday-banner" has been emergency disabled` when done from the detail page (`pages/FeatureDetail.tsx:317`).
- Policy banner inside the emergency dialog: on camera both the disable and the enable dialog show the banner "Approval required" (title, `Matched policy requires manual approval`, policy `Release approvals`, scope `All environments`) with the badge "Emergency disable" or "Emergency enable". It is misleading, so the voiceover says it is only a preview. Cause: the dialog calls `previewApprovalPolicy` with `changeType: 'emergency_action'` and a stage status (`ROLLBACK_REQUESTED` for disable, `DEPLOYMENT_REQUESTED` for enable) for the first Production stage as a stand-in (`modals/FeatureEmergencyActionModal.tsx:60-68,126-130`, banner at `:235-241`). The backend validates the change type and then ignores it: it previews a stage change (`rest/approval.rs:1004,1015-1018`; `logic/approval.rs:2306-2370`), and both statuses are intercepted (`status_requires_interception`, `logic/approval.rs:59-61`), so any applicable policy previews as requires approval. The emergency handlers themselves create no approval request and run no freeze check; they require only an admin or `Team Admin` and a reason of 5 to 500 characters (`rest/feature.rs:70-96,1798-1978`; `logic/feature_tx.rs` has no approval or freeze call at all; its only match for approval is a `None` field at `:113`). No freeze is active at that point in the script (the window was disabled earlier), but the claim holds in any order. In the dialog, zoom on "Reason" (`:247`) and "Disable timing" (`:271`), the two fields that matter, and do not read the banner out. The banner is a product quirk, not a recording error.
- Gate beat: `gate.sh` (video 09, block A) calls the backend `POST /api/v1/evaluate` with the `ci-bot` token for the Development environment and prints `banner on` or `banner off`, exiting 0 or 10. With Development deployed and the kill switch on, the flag evaluates to `true` and the script exits 0; with the kill switch off the result is `false` (`feature-toggle/evaluation-engine/src/lib.rs:817-826`) and the script exits 10. The exit-10 path was checked live on v1.2.0 in the video 09 smoke test (flag not deployed); the exit-0 path after a deployment was not run: confirm it once before recording, and cut the gate sentences from the voiceover if the flag does not evaluate to on after the deployment. The `ci-bot` token lives 30 days; if you re-record later, create a fresh token.
- Scheduled Changes (`FeatureCreate.tsx:2297-2425`): section title "Scheduled Changes", count text `0 scheduled change(s)`, labels "Action", "Run At", "Reason", button "Schedule Change", toast "Scheduled change created". "Action" defaults to "Disable feature" (`:473`, labels at `:138-143`) and "Run At" to one hour from now (`:474`), so change "Run At" to next week. The table columns are "Action", "When", "Status", "Reason", "Actions"; the new row shows "Pending", and the row button "Cancel" shows the toast "Scheduled change cancelled" and the status "Cancelled". The section is on the edit page only; the detail page lists active ones under "Scheduled Changes" read-only. A "Reason" is required.
- Version History (`components/features/FeatureHistoryPanel.tsx`): tab "History" on the edit page (`FeatureCreate.tsx:1533`), and the "Activity" tab on the detail page (`FeatureDetail.tsx:484,746`), next to an "Audit Snapshot" card. The panel shows each version as `Version <n>` (built at run time) with a source tag ("Update", "Kill switch" or "Rollback", `:49-58`); selecting one loads `Version <n> Diff` against the previous version with "Before" and "After" panes. It does not diff two arbitrary versions, so the script reads one version's diff and rolls back to the one before. The button reads "Rollback" (or "Current Version" when the newest is selected, `:202`) and asks `window.confirm`; the toast reads "Feature rolled back". Because the confirm text is built at run time (`:155`), the script does not quote it.
- What creates a version: an "Update Feature" save, each emergency disable and enable (tag "Kill switch"), stage-criteria saves and rollbacks (`logic/feature_tx.rs:706,832,977,1059`, `rest/criteria.rs:622,746`). Creating the feature and stage changes do not. With this script `holiday-banner` ends with versions from the emergency disable, the emergency enable, the description update and the rollback. Select the version just before the update, that is the one tagged "Kill switch" from the enable, not the one from the disable (that version holds the disabled state and would switch the flag off again). Version numbers can differ if you edited the flag earlier, so the voiceover gives none.
- The rollback also restores the description only, because nothing else changed since that version. If you want a more visible diff, change the description by a few words rather than one character.
- Make sure no freeze is active before "Update Feature": the script ended the window earlier, and an active freeze on any of the flag's environments would ask for an override reason (`rest/feature.rs:1673-1688`).
- After switching users, reload the page if the team selector looks stale.
