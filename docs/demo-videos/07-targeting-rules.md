## Gotchas while recording

- Blocker for the continuity table: without an approval policy a stage cannot reach DEPLOYED through the UI or the REST API. "Request Deployment" moves the stage from NOT_DEPLOYED to DEPLOYMENT_REQUESTED directly, because `maybe_create_stage_change_request` returns nothing when no policy applies (`feature-toggle-backend/src/logic/approval.rs:1838-1841`) and the code falls through to "No approval gating: validate and apply directly" (`src/logic/feature.rs:2002-2030`). From DEPLOYMENT_REQUESTED the only transitions are DEPLOYMENT_REJECTED and DEPLOYMENT_APPROVED (`src/validation.rs:59`), and nothing outside a policy vote or a trusted Jira "approve" produces DEPLOYMENT_APPROVED (comment at `src/logic/approval.rs:2509-2511`; `feature-toggle/docs/jira-integration/setup-guide.md:93` says the same). The "Deploy" action only appears for DEPLOYMENT_APPROVED (`feature-toggle-ui/src/pages/FeatureCreate.tsx:759-762`), so the Actions menu for the stage says "Approver role required to review requests" (`FeatureCreate.tsx:2026`). The brief expected "Request Deployment" to auto-approve; the code does not. As recorded, this script ends with Development at DEPLOYMENT_REQUESTED, which contradicts the End state "Development stage deployed" copied from the continuity table and the start of video 08. Options for the series owner: (a) move policy creation and an approval by `sam` ahead of this video (breaks the continuity rows for 07 and 10); (b) change the backend so a request with no policy approves itself; (c) deploy Development through a Jira approve in a later video. The "Approval policy preview" banner on the selected stage says "No approval required" in this state (`features/ApprovalPolicyPreviewBanner.tsx:19-22`), which misleads; do not read it aloud.
- Accounts: the criteria endpoints have no role check, so `priya` can save criteria (`PUT /stages/{id}/criteria`; the route policy only guards `PATCH`, `feature-toggle-backend/src/logic/policy.rs:394`). Requesting a deployment needs the Requester role (`src/logic/authorization.rs:212-227`), and the UI hides the action without it, so `admin` (no Requester role) cannot do that step. Saving a rollout template needs a system admin or `Team Admin` (`src/rest/rollout_template.rs:172-186`), so `priya` gets a 403 there. That is why the script switches to `admin` for the last two scenes.
- Deviation from the brief: the brief saves the template, then clicks "Apply Template" on the Staging stage to copy the criteria. The code cannot do that. A rollout template holds only the stage plan (environment ids, order, positions, bucketing key; `features/RolloutTemplatePicker.tsx:179-196`), never criteria. "Apply Template" needs a preview of at least one environment, then replaces the whole stage graph with new, unsaved stages and clears the criteria (`FeatureCreate.tsx:1304-1341`). Running it on the edit page would detach the stages from the saved ones, so the script does not use it, and instead repeats the criteria on Staging. "Save Current As Template" is the label of the name field, and the button reads "Save" (`RolloutTemplatePicker.tsx:398-419`); the toast reads "Rollout template saved". The name `plus-first-then-20` therefore says more than the template stores; the voiceover says so.
- Deviation from the brief and the continuity table: the priority numbers in the UI start at 0. The first criterion shows "Priority 0" and the second "Priority 1" (`FeatureCreate.tsx:268`, built as `Priority {row.priority}`; `handleAddCriterion` starts at 0, `FeatureCreate.tsx:548-556`; reordering renumbers from 0, `pages/feature-create/criteria.ts:132-145`). The continuity row says priority 1 and 2; the voiceover avoids the numbers. Runtime-built labels for `Label exceptions`: "Priority 0" and "Priority 1" (`FeatureCreate.tsx:268`), "Criterion 1" and "Criterion 2" (`FeatureCreate.tsx:267`), "Rule Group 1" (`components/CompoundRuleBuilder.tsx`, `Rule Group {groupIndex + 1}`).
- A new criterion starts collapsed, so click "Expand" (`FeatureCreate.tsx:555`). A new criterion defaults to "Weighted Split" with an even split of the variants. Choosing "Specific Variant" preselects the first variant, `classic` (`FeatureCreate.tsx:332`), so switch it to `express`. "Distribute Evenly" is disabled with fewer than two variants (`components/VariantAllocator.tsx:130`). The weighted split is rejected if it totals over 100 or has fewer than two variants with weight (`criteria.ts:223-241`).
- "Add Rule Group" creates a group with `AND` and one empty condition whose key defaults to the first available context key (`CompoundRuleBuilder.tsx:91-107`), so overwrite the "Context Key" field with `country`. "Context Key" is free text with suggestions, "Operator" is a select that includes "Equals", and "Value" is free text. "Add Condition" adds another row (`CompoundRuleBuilder.tsx:479-490`); the second button, "Add Rule Group (OR)", adds an alternative group. A criterion with no rule groups matches everyone (`feature-toggle/evaluation-engine/src/lib.rs:542-548`).
- Evaluation order: criteria are checked in ascending priority and the first match wins (`evaluation-engine/src/lib.rs:540-571`; `fluxgate.wiki/Priority-Evaluation.md`).
- "Save Stage Criteria" shows the toast "Stage criteria saved" (`FeatureCreate.tsx:1138`). Clicking another stage reloads criteria from the server, which discards unsaved edits (`FeatureCreate.tsx:1100-1109`).
- The "Actions" menu appears once a stage is selected. After "Request Deployment" the toast reads "Stage change requested" (`FeatureCreate.tsx:1028`). The optional "Stage Change Details" fields ("External Reference", "Reason") can stay empty. The "Update Feature" button needs an admin or `Team Admin` (`PATCH`), so do not click it as `priya`.
- After switching users, reload the page if the team selector looks stale.
